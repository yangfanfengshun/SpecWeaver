# SpecWeaver v0.8.0

> **需求工作流大改版，强烈建议所有用户更新。**

v0.8.0 重新设计了从 Tower 读取、蓝湖/Eolink 收集到需求分析的完整链路。资料收集与
Agent 分析正式拆成两个独立动作：来源读取、格式化、下载、命名、排序和验证全部交给
确定性脚本，模型只在用户明确要求分析时介入。

这次改版的直接收益是：收集阶段不再把 Tower 全文、设计大对象和接口集合反复塞进
模型上下文，能够显著减少不必要的 Token 消耗，同时避免 Luna、Sol 等不同模型导致
收集文件出现差异。实际节省量取决于需求规模和所用宿主，但评论、设计稿和 API 越多，
收益越明显。

## 为什么强烈建议更新

- **更省 Token**：机械收集由脚本完成，Agent 只接收状态、数量和路径；用户只想收集
  资料时，不再触发完整需求分析。
- **结果更稳定**：相同来源、范围和脚本版本会生成相同产物，收集结果不受模型能力和
  表达差异影响。
- **项目更干净**：机器专用清单与设计结构进入用户缓存，项目只保留开发真正需要的
  Tower 原文、附件、API、预览图和切图。
- **流程更可控**：Bug 自动快速处理；普通需求按用户意图选择快速分析或完整收集；
  `requirement.md` 只有在用户确认分析后才生成。
- **安全边界更完整**：输出目录与用户缓存增加符号链接防护，失败来源、旧文件更新和
  本地产物验证都有明确状态。

## 本次更新

- Tower 读取会在 `~/.specweaver/cache/tower/<任务ID>/` 原子生成可读
  `tower-raw.md` 与机器用 `tower-metadata.json`；原文不再嵌入 Base64 元数据。
- Tower MCP 不再把全文和附件二进制复制进工具结果，只返回缓存路径、任务类型、数量、
  来源线索和读取状态。
- 新增统一需求收集 MCP：范围未确认时只列候选，确认后一次性编排 Tower 附件、蓝湖
  结构/预览/切图和 Eolink API，并把可验证清单保存到用户缓存。
- 用户缓存只保留轻量 Markdown/JSON：需求清单按 Tower ID 与项目输出目录隔离，蓝湖
  规范化结构按 `image_id` 独立复用；图片、切图和附件仍写入项目。
- Eolink 改为每个接口一个 `<API-ID>-<接口名称>.json`；蓝湖预览图和切图使用
  `<设计名称>--<image_id>` 命名。
- `requirement-collection` 负责快速路线和确定性收集，到来源验证结束即停止；新增
  `requirement-analysis`，只有用户确认后才读取项目来源并生成 `requirement.md`。
- Bug 只由明确 `Bug` Tag 识别；其他任务默认普通需求，按用户意图选择快速分析或
  完整收集。
- 蓝湖设计实现改为从用户缓存清单发现已确认设计，不再依赖项目内
  `collection-manifest.json` 或旧 `design-context.json`。

## 重要变化

- 项目目录不再生成 `collection-manifest.json`、`tower-attachments.json` 和
  `design/`；这些机器信息分别迁移到需求清单缓存和蓝湖独立缓存。
- Eolink 从“一个来源链接一个聚合文件”调整为“一个 API 一个文件”，旧的
  `eolink-NNN.json` 会在成功更新时由脚本清理。
- Tower 缓存从单个混合文件调整为干净的 `tower-raw.md` 与独立
  `tower-metadata.json`，原文更适合直接阅读和分析。
- 用户缓存只保存轻量 Markdown/JSON，不缓存图片、切图或附件；删除缓存后需要重新
  收集对应来源。

如果仍在使用 v0.7.x，建议直接更新到 v0.8.0 后重新收集正在开发的需求资料，以获得
新的缓存结构、确定性产物和更低的 Token 开销。

## 验证结果

- 通过 Tower 评论边界、引用和元信息格式化测试。
- 通过轻量缓存边界、工具小型返回、候选确认、受限附件确认和来源文件验证测试。
- 通过同一输入重复收集的逐文件哈希一致性测试。
- 通过 Eolink 混合成功/失败更新、输出目录与缓存符号链接防护测试。
- 通过插件清单、Skill 架构、安装生命周期、版本一致性和 133 项全量回归测试。
