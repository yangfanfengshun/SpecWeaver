# Tower 需求资料收集

## 边界

- 把一个 Tower 任务作为一个独立任务处理。
- 只使用 Tower、蓝湖、Eolink 和用户明确补充的事实；标出来源，不按经验补全。
- 不发布 Tower 评论，不分析代码范围，不制定技术方案、开发计划或工期。
- BUG 或快速模式只在对话中回答；完整模式才创建资料目录。
- 完成当前路线后立即停止，不进入后续开发工作。

完整模式生成文档前读取 [需求文档模板](references/requirement-template.md) 和 [API 文档模板](references/api-template.md)。快速模式不要加载模板。

## 状态机

严格按以下状态转换，不满足门槛时暂停，不跳步：

```text
TOWER_READ
→ TYPE_DECIDED
→ MODE_SELECTED
→ MATERIAL_SCOPE_CONFIRMED        # 仅完整模式
→ MATERIALS_COLLECTED             # 仅完整模式
→ DOCUMENTS_WRITTEN               # 仅完整模式
→ VERIFIED                        # 仅完整模式
→ DONE
```

始终保存已读取事实和用户选择。认证更新或用户回答后从当前失败状态继续，不从头重复询问。

## 1. 读取 Tower 并判断类型

1. 验证输入是 Tower 任务链接。
2. 调用 `tower_read_todo(url, include_images=false)`，读取分类、正文、全部评论、子任务、附件清单和外部链接；此时不得下载或逐张读取图片。
3. 检查全部分类：只要任一分类名称与 `BUG管理` 完全一致，就判定为 BUG；分类为空、缺失或无法确认时按普通需求处理。不要根据标题猜类型。
4. 从已读文本中识别蓝湖链接、Tower 原型、Eolink 链接、API ID 和多组资料线索。
5. 调用 `lanhu_check_auth()` 只确认能力状态；返回 `disabled` 时记为“本机未启用蓝湖能力”，不把它当成缺失或认证失败。

## 2. 选择处理模式

### BUG 管理

自动进入快速模式，不询问深度。调用 `tower_read_todo(url, include_images=true)` 实际查看附件，输出 Bug 摘要、触发条件、当前表现、期望表现、影响范围、证据和未明确事项。未提供的事实写“未明确”。不得读取蓝湖或 Eolink，不创建文件。输出后进入 `DONE`。

### 普通需求

展示从 Tower 判断出的资料状态，并让用户选择：

1. 快速分析：只分析 Tower，在对话中回答，不生成文件。
2. 完整资料收集：确认资料范围，读取蓝湖与 Eolink，生成完整资料。

存在蓝湖、Eolink、多页面或复杂业务规则时推荐完整模式；内容短、改动明确且无外部资料时可推荐快速模式。推荐不等于替用户选择。

需要选择时优先调用宿主平台的原生用户选择工具；工具不可用时使用编号文字。提供互斥选项、简短说明和一个推荐项。提问后暂停，收到回答前不得继续。

用户选择快速模式后调用 `tower_read_todo(url, include_images=true)`，分析 Tower 全部内容和必要图片，直接回答并进入 `DONE`。不得读取蓝湖或 Eolink，不创建目录。

## 3. 确认完整模式资料范围

先检查目标目录中是否已有同一 Tower 任务的 `requirement.md`；若其中明确记录了资料状态、采用范围和依据，且 Tower 未出现改变范围的新资料，则复用选择，不重复询问。

按以下优先级判断设计状态：

1. `LANHU_ENABLED=false`：状态为“本机未启用蓝湖能力”，不询问、不读取蓝湖。
2. Tower 含蓝湖链接：状态为“已发现”。调用 `lanhu_get_designs` 获取设计名称和分组候选，但不要下载图片。
3. 无蓝湖但有 Tower 原型：状态为“Tower 原型待确认”。
4. 两者都没有：状态为“未发现”。

API 含 Eolink 链接或 API ID 时为“已发现”，否则为“未发现”。

- 设计和 API 已存在且采用范围唯一明确：直接继续。
- 只有一项缺失：只询问该项。
- 两项都缺失：在同一次交互中询问两项。
- 设计或 API 存在多组且无法从正文、评论或名称确定关联：整理候选清单，在同一次交互中询问采用范围。
- Tower 有原型但无蓝湖：提供“使用 Tower 原型”“补充蓝湖链接”“确认无设计资料”。
- API 缺失：提供“补充资料”“等待后端”“不需要”“不涉及”。

只询问实际缺失或范围不明的内容。允许自由输入、取消和改变选择；无效回答时说明问题并继续等待，不擅自选择。把最终采用、未采用的资料、判断依据和用户确认记录到后续 `requirement.md`。

范围未确认前不得调用 `tower_download_images` 或 `lanhu_download_design_images`，不得生成文档。

## 4. 处理认证问题

区分 `missing_config`、`disabled`、`auth_expired`、`forbidden`、`network_error` 和资料缺失。

- Tower 认证失效：暂停整个流程，提示运行安装插件中的 `scripts/setup.sh --configure`，更新后从 `TOWER_READ` 重试。
- 蓝湖认证失效：暂停蓝湖步骤，让用户选择更新后重试，或明确确认本次不采用蓝湖；不得自动改成“无设计稿”。
- Eolink 认证失效：暂停 API 步骤，让用户选择更新后重试，或明确确认本次不采用 API；不得自动改成“无 API”。
- 不输出 Cookie、密码、登录响应或其他敏感值；认证失败后不要盲目重复请求。

保留已读取 Tower 内容、已确认范围和已成功下载资料。用户明确放弃资料时记录选择和原因。

## 5. 收集已确认资料

创建 `docs/tower/<Tower原始标题>/images/`，只替换操作系统禁止的目录字符。

1. 调用 `tower_download_images` 保存全部 Tower 附件；逐张查看成功保存的本地图片。
2. 对每个采用的蓝湖项目调用 `lanhu_get_designs`，只选择已确认范围内的设计，再调用 `lanhu_download_design_images`；逐张查看本地原图。
3. 对每个采用的 Eolink 链接调用 `eolink_read_url`；只有 API ID 时调用 `eolink_get_interface_by_id`。
4. 保留所有来源 URL、本地文件映射、失败原因、API 字段类型、方向、单位、枚举、必填条件和备注。
5. 不下载未采用的设计或 API 资料；相同图片内容只保留一个本地文件。

多张设计图要识别页面、Tab、弹窗、分区、步骤和状态之间的层级，不只罗列图片名称。

## 6. 生成文档

固定结构：

```text
docs/tower/<Tower任务名称>/
├── requirement.md
├── api.md
└── images/
    ├── tower-001.png
    └── lanhu-001.png
```

- 按模板生成 `requirement.md` 和 `api.md`，删除占位说明和未使用行。
- 使用相对路径双向关联两份文档，并将每张成功图片以 `./images/<文件名>` 写入证据索引。
- API 状态为等待后端、不涉及或明确无资料时仍生成 `api.md`，只写状态与依据，不生成空接口。
- 同一 Tower 任务重复运行时更新同一目录；只更新文档和工具管理的 `tower-*`、`lanhu-*` 文件，不删除其他人工文件。
- 不把 Skill 规则、插件实现、开发计划或代码分析写入需求资料。

## 7. 完成前验证

逐项验证并保留可说明的证据：

- Tower 正文、全部评论、子任务、资料状态和采用范围已完整处理。
- `requirement.md`、`api.md` 和所有声明成功的本地图片真实存在。
- 文档中的 API 链接和图片相对路径都能解析到真实文件。
- 每张图片能追溯到原始来源，失败项记录了原因。
- 设计、API、冲突、缺失和用户选择均有明确状态。
- 文档未混入实现建议、开发计划、代码分析或插件内部规则。

任一检查失败时修复或明确报告阻塞；没有验证证据时不得声明完成。全部通过后进入 `DONE`。
